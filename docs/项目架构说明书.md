## 一、这个系统是干什么的

这是一个**配电网故障处理辅助决策系统**。通俗解释：

1. **配电网**：城市里把 10kV 高压电降压后送到小区/工厂的电网，标准模型是 IEEE 33 节点（33 个配电变压器 + 32 条主干线路 + 5 条备用联络线）。
2. **故障**：某条线路短路或断开了（比如 8 号杆和 9 号杆之间的线路）。
3. **转供**：故障点下游的用户停电了，操作员需要找一个"备用路径"（联络开关）把电从另一条路送过去。
4. **操作票**：操作员执行的一系列开关操作步骤（断开故障线 → 合上联络开关 → 核查电压负载），每一步都要记录在案，类似"电力行业的施工工单"。
5. **安全校验**：合上联络开关后，会不会让某条线路过载？电压会不会太低？必须用潮流计算验证。

**一句话总结**：输入一条故障线路 → 系统自动分析哪些用户停电了 → 找到备用供电路径 → 生成操作步骤 → 校验安全性。

## 五、核心概念解释

### 5.1 IEEE 33 节点配电网

标准的测试配电网模型，33 个节点（配电变压器）、32 条主干线、5 条联络线（常开，故障时用来转供）。

```
     Bus-01 (电源)
      ├─ 02─03─04─05─06─07─08─09─10─11─12─13─14─15─16─17─18
      │              │        │                    │
      │              │        │                    └── T4/18-33 联络
      │              │        └── T1/8-21 联络
      │              └── 26─27─28─29─30─31─32─33
      │                          └── T5/25-29 联络
      ├─ 19─20─21─22
      │       └── T3/12-22 联络
      └─ 23─24─25
```

联络开关：T1(8-21)、T2(9-15)、T3(12-22)、T4(18-33)、T5(25-29)

### 5.2 BFS 故障分析

"从电源出发，沿着闭合的线路能走到哪些节点"——走不到的节点就是停电区。

1. 把所有 status=1（闭合）的线路建成邻接表（图）
2. 故障线路强制断开（不加入图）
3. 从 BUS-01 做广度优先搜索 (BFS)
4. 访问不到的节点 = outage_nodes（停电节点）

### 5.3 联络开关与转供

停电区被故障隔离后，合上某个常开的联络开关，就能从另一条路径送电。

例如：故障 27-28 → 28~33 停电。合上 T4(18-33) → 33 节点重新带电 → 28~33 全部恢复。

### 5.4 评分体系 (100 分制)

| 维度 | 满分 | 说明 |
|------|------|------|
| 恢复率 | 45 | 能恢复多少停电负荷 |
| 负载率 | 20 | 联络线会不会过载 |
| 电压质量 | 20 | 恢复区电压是否 ≥0.95pu |
| 操作次数 | 10 | 单开关 10 分，双开关 8 分 |
| 完全恢复奖励 | 5 | 所有停电节点都恢复了 +5 |

### 5.5 算法来源标记

每个接口返回的 `algorithm_source` 字段标记了数据来源：

| 值 | 含义 |
|----|------|
| `external` | 张同学算法服务成功返回结果 |
| `external_pending` | 张同学异步任务已提交但尚未完成 |
| `local_fallback` | 外部服务未配置/不可用，使用本地规则兜底 |
| `local_rule` | 本地规则评分 |
| `unavailable` | 外部服务不可用或接口未实现 |

### 5.6 工作流 7 步骤

```
1. 故障输入 → 2. 边界判定 → 3. 转供决策 → 4. 操作序列
→ 5. 模板成票 → 6. 安全校验 → 7. 导出归档
```

页面间通过 `localStorage` 传递数据：
- `current_fault_line`：选中的故障线路
- `current_selected_plan`：用户确认采用的转供方案
- `current_operation_steps`：生成的操作步骤
- `current_ticket`：生成的操作票
- `current_safety_check`：安全校验结果

## 六、后端架构详解

### 6.1 main.py 结构（最重要的文件）

`backend/main.py` 是后端核心，约 1700 行。按功能分块：

```
1. 导入 + FastAPI 初始化 (行 1-40)
2. 线路归一化工具 (行 42-78)
   - parse_line_pair("28-27") → (27, 28)
   - normalize_line_key("28-27") → "27-28"
3. 联络线容量表 (行 63-78)
   - T1-T4: 1200kW, T5: 500kW
4. 外部评分缓存 + 过期判断 (行 80-101)
5. _build_local_forecast() — 本地预测 (行 106-171)
6. forecast_realtime — 源荷预测端点 (行 182-275)
7. _run_local_fault_bfs() — 本地 BFS (行 277-315)
8. fault_analyze_realtime — 故障分析端点 (行 390-430)
9. boundary_analyze_realtime — 边界判定端点 (行 555-640)
10. transfer_recommend_realtime — 转供推荐端点 (行 690-830)
11. transfer_evaluate_realtime — 转供评分端点 (行 845-1100)
12. 算法任务查询端点 (行 840-950)
13. safety_validate_realtime — 安全校验端点 (行 1337-1439)
14. 外部评分接收 + 操作序列生成 + Dashboard 摘要
```

### 6.2 关键工具函数

| 函数 | 位置 | 作用 |

## 七、前端架构详解

### 7.1 页面路由

| 路径 | 页面组件 | 说明 |
|------|---------|------|
| `/` | Dashboard.tsx | 首页驾驶舱，4 秒轮询实时数据 |

| `/ticket` | TicketGeneration.tsx | 模板化成票 |
| `/safety` | SafetyCheck.tsx | 安全校验 |
| `/data` | DataManagement.tsx | 数据管理 |

### 7.2 TransferDecision.tsx 核心流程

```
用户选择故障线路 (下拉框/手动输入)
  → 点击"执行转供决策"
    → 并行调用:
      ① POST /api/transfer/recommend-realtime (拿 pending/评分)
      ② POST /api/transfer/evaluate-realtime (拿候选方案/故障摘要)
    → 合并结果:
      - 候选方案来自 evaluate
      - pending/job_id 来自 recommend
    → 展示:
      - 外部候选方案 (ALG-001, ALG-002, ALG-003)
      - 如果 external_pending: 蓝色 pending 卡 + 查询任务结果按钮
      - 本地规则方案 (T1/T2/T3 等, 标注"规则版预评估")
  → 选择方案 → "生成转供预案" → 写入 localStorage → 进入操作序列页面
```

### 7.3 localStorage 数据流

```
拓扑图选择故障线
  → localStorage.current_fault_line = "13-14"
  → 转供决策页读取，确认方案
    → localStorage.current_selected_plan = {...plan, fault_line}
    → localStorage.current_transfer_result = {...result}
    → 操作序列页读取 selected_plan
      → POST /api/sequence/generate
      → localStorage.current_operation_steps = [...steps]
      → localStorage.current_sequence_result = {plan_id, tie_lines, ...}
      → 模板成票页读取 operation_steps
        → localStorage.current_ticket = {ticket_id, ...}
        → 安全校验页读取 current_ticket
          → localStorage.current_safety_check = {...}
```

### 7.4 safetyRules.ts 校验引擎

独立于 UI 的纯函数模块，8 项校验：

1. 操作票完整性（7 个必填字段）
2. 故障隔离确认（操作序列含 verify_open 步骤）
3. 联络开关闭合操作（tie_lines 逐条有对应 close 步骤）
4. 操作顺序（隔离→合闸→核查）
5. 转供方案可用性（is_usable / radial_ok / overloaded / violations）
6. 电压校验（≥0.95pu）
7. 负载率校验（≤100%）
8. 外部评分可信性（external_matpower / local_rule）

## 九、关键约束（修改代码时务必遵守）

1. **永远不要改** `/api/realtime/update` （Simulink 数据入口）
2. **永远不要改** `_verify_simulink_token()` （Simulink 认证逻辑）
3. **不要把真实 Key 写进代码**（Key 只在 `.env` 中）
4. **不要把算法服务地址写在浏览器能看到的代码里**
5. **外部服务离线时返回 HTTP 200 JSON，永远不要 502**
6. **不要删除** `topologyData.ts`（33 节点静态拓扑）
7. **不要伪造**潮流校验结果（safe 不为 true 就不能出正式票）

## 十、学习路径建议（给新手）

1. **先跑起来**：启动后端 + 前端，打开浏览器看看每个页面长什么样
2. **理解数据流**：打开 F12 Network 面板，看每个页面点击按钮后发了什么请求
3. **读 main.py**：从 `forecast_realtime` 开始（最简单），再到 `fault_analyze_realtime`（BFS），最后 `transfer_evaluate_realtime`（最复杂）
4. **读前端 TransferDecision.tsx**：理解前后端如何配合
5. **跑测试**：`integration_test.py --seed-test-data` 看 7 个接口的请求/响应
6. **改一个小功能**：比如在 Dashboard 上加一个指标卡片，理解完整链路
